# 移动端功能分区与执行环境设计

更新：2026-09-13。依据：[实际客户端功能盘点](05-current-feature-inventory.md)。状态：第二轮产品建议，尚未实现，也不视为用户已批准全部布局与范围。

技术栈已确定：React Native + TypeScript + Expo development build，Android 优先，兼容 iOS。文件、记忆和执行环境沿用各自独立的产品含义。

## 建议四个主入口

建议从上一版三个入口调整为 **首页 / 会话 / 资源 / 管理**。新增资源入口，是因为实际产品里的文件与执行电脑都属于日常工作对象；只放在系统设置中会让“查看结果”和“找到运行位置”过深。

| 主入口 | 回答的问题 | 主要内容 |
| --- | --- | --- |
| 首页 | 现在有哪些任务，有什么需要我处理？ | 继续上次会话、待处理、运行中、新结果、定时任务入口 |
| 会话 | 我要继续哪个对话？ | 当前 Team 的会话列表、Bot 筛选、搜索、固定/文件夹、创建会话 |
| 资源 | 文件和执行环境在哪里？ | 文件、执行环境两个子入口；最近查看的文件与关联会话 |
| 管理 | 我要调整哪个 Bot 或服务？ | Bots、能力与服务、团队与成员、用量、账号和 App 设置 |

首页保留用户已确认的“并行任务与深入聊天兼顾”。它与会话页可以复用会话行，但首页按“需要注意的事”组织，会话页按“查找历史”组织。

不增加单独的 Agent、Workspace、Memory、Schedule、Artifacts 五个底部标签。它们都有入口，但分别附着在用户当前的工作对象上，避免主导航过载。

冷启动仍恢复上次有效页面；首页不是每次回前台的强制落点。深度聊天、阅读器和长表单采用全屏栈导航，必要时隐藏底部栏以保留输入空间；返回时回到原入口和原位置。

## 上下文层级

部署与账号共同确定登录上下文，Team 是当前工作范围；Bot、Session 和执行位置按任务选择。不要在每个页面顶端堆出五层选择器。

```text
部署 / 账号
└─ 当前 Team
   ├─ 首页：聚合该 Team 中已授权的任务
   ├─ 会话：全部 Bot / 指定 Bot → Session
   ├─ 资源：选择 Bot → 文件所在环境 / 可用执行环境
   └─ 管理：Bots / 连接服务 / 团队 / App

一个聊天上下文
  Bot → Session → 当前 Agent / 本次模型 / 本次执行位置
```

Team 切换放在顶层标题菜单；部署和账号切换放在同一菜单的连接管理页。只有一个 Team 时弱化选择器，不要求用户在每次启动时逐级选择。

Bot 详情是一级业务页面，不只是设置表单。首页会话行、聊天标题、资源来源和管理的 Bot 列表都能进入它；内容包括概况、会话、记忆、任务、可用执行环境与能力。只有真正的配置进入“Bot 设置”。

当前桌面有 Bot 和其下的 Agents 两层。移动端第一次遇到时可以说明：“Bot 保存会话与配置；Agent 决定用哪种执行实现。”不要直接把所有 Bot 改名为 Agent，再让内部 Agent 使用同一名字。

## 首页与自动化

首页建议按以下顺序提供少量摘要，点击后进入完整列表：

1. 继续上次会话：恢复原阅读位置。
2. 等你处理：待回答、待审批、需要关注的异常。
3. 正在运行：主要阶段、Bot、执行位置、状态更新时间。
4. 新结果与最近会话：完成摘要、文件产物入口。

定时任务是自主 Agent 的重要入口，放在首页可见的“定时任务”按钮/筛选，也可从 Bot 详情进入。普通聊天、服务端排队任务、定时定义与某次定时执行是不同对象，不能用同一个“任务”状态字段硬拼。

定时任务列表建议显示任务名、所属 Bot、启用状态、下一次执行时间和上一次结果；展开执行记录进入对应会话。跨 Bot 聚合、下一次执行及历史记录的具体返回能力需验证，属于移动端要求，不是本轮已确认的现有 API。

创建表单采用“指令与 Bot → 时间 → 执行选项 → 核对”的全屏流程。每日/每周等常用频率前置；cron 放高级项；时区必须明确。已有表单的模型、运行会话和次数限制保留，不因移动化而悄悄改变含义。

## 会话内的三种选择

| 选择 | 用户需要知道什么 | 建议交互 |
| --- | --- | --- |
| Agent | 使用内建 Memoh，还是某个已配置外部 Agent；是否改变会话归属/需要新会话 | 会话信息中展示，创建会话时可选；现有会话切换遵循服务端语义 |
| 模型与推理强度 | 对什么 Agent 有效，对本次还是后续生效 | 输入区精简标签 → 选择面板，只展示当前 Agent 支持的选项 |
| 执行位置 | 文件和命令在哪台环境中运行 | 输入区位置标签 → 带状态与权限说明的电脑选择面板 |

桌面 General 明确说明默认 Agent 用于新的本地聊天，已有会话保留其 Agent。移动端应保留这一规则；不能把修改 Bot 默认 Agent 包装成正在运行的聊天即时切换。

选择位置时显示 Cloud Computer 或具体电脑名称、在线状态、允许的操作和默认标记。用户选择一次执行位置，不应隐式修改 Bot 的默认位置；如果上游当前语义不同，需先对齐协议再定义界面。

位置变更必须在用户发送前可见。离线 outbox 保存创建时的 Agent/模型/位置意图，不因用户后来切换 Bot、Team 或电脑就改投目标。恢复后若目标不可用，等待或提示重新选择，不静默改用另一台机器。

## 资源：文件

文件页以当前 Bot 与明确的文件位置为上下文。首屏优先最近访问/产物入口与目录列表，目录使用面包屑和栈式前进；手机不维持一棵永远展开、层层缩进的侧栏树。

```text
┌──────────────────────────────┐
│ 资源                         │
│ 文件             执行环境    │
│ Bot A ▾   Cloud Computer ▾   │
│ 搜索当前范围…                │
│                              │
│ 最近查看                     │
│ report.md     来自：任务 A  › │
│                              │
│ Cloud Computer / 项目目录     │
│ 📁 assets                  › │
│ 📄 report.md               › │
│ 📄 result.json             › │
│                              │
│ 上传 / 新建                  │
└──────────────────────────────┘
```

上图的最近文件、来源关联与跨位置浏览是移动建议。当前实际 Files 页面只确认了 Bot 文件树，不能假设连接的每台电脑都已具备相同的文件列表协议；按能力展示可浏览的位置。

从聊天点文件卡片打开全屏阅读器，保留“来自哪个会话、哪个环境、哪个路径”。从资源页打开同一文件则返回资源页。聊天锚点、文件阅读位置和目录位置分别保存，不共用一个返回目标。

初版优先 Markdown/纯文本、代码、图片、小文件上传、下载与系统分享。HTML/PDF 等复杂预览按单独查看器适配；完整代码编辑、批量管理和文件夹上传后续再做。

有三个对象应分清：

- **工作文件**：执行环境里的可变文件，Agent 可能继续修改它。
- **聊天中的文件引用**：关联某次输出，是否指向固定版本需由服务端明确。
- **本地下载副本**：手机上保存的某一版本，可能已经与远端不同。

不把聊天卡片天然当成不可变 Artifact。需要不可变版本时，补充 asset/revision 语义；离线可读时注明缓存时间或版本。删除/重建 Workspace 后，持久附件是否仍能访问也应有明确契约。

编辑工作文件时，服务端 revision/ETag 和冲突处理是前提。Agent 与手机同时修改时展示冲突或新版本，而不是后写覆盖；首版阅读优先可以降低这一风险。

## 资源：执行环境与 Workspace

“执行环境”是移动产品入口，内部区分 Bot 内建 Cloud Workspace 与连接电脑。保留真实类型，不能让所有环境看起来都能使用相同的运维按钮。

```text
┌──────────────────────────────┐
│ ‹ 执行环境                   │
│ Cloud Computer               │
│ Bot A · 运行中               │
│ 刚刚同步                     │
│                              │
│ 正在此处执行                 │
│ 任务 A · 正在检查文件       › │
│                              │
│ 文件                       › │
│ 允许的操作                 › │
│                              │
│ 资源监控：此环境暂不支持      │
│                              │
│ 高级管理                   › │
│ 资源限制 / 快照 / 环境详情    │
└──────────────────────────────┘
```

环境列表显示类型、所属 Bot/可用 Bot、状态、新鲜度与当前任务摘要。跨 Bot 关联、正在执行的任务和权限摘要需要聚合能力支持。不能仅因为一台电脑 Online，就推断某次 run 正在正常工作。

对于连接电脑，首屏展示连接状态、允许哪些 Bot 使用、工作位置及可用能力；对 Cloud Workspace，才在有权限且后端支持时展示资源限制、快照和生命周期动作。手机默认承担观察和控制职责，不照搬桌面全局 Computers 的“This computer 可运行命令”注册体验。

以下状态单独表示：

| 状态 | 显示与处理 |
| --- | --- |
| 在线、状态新鲜 | 可以根据能力发起操作 |
| 上次在线、正在同步 | 保留缓存与时间，等待重新核对 |
| 确认离线 | 文件可看已下载副本，控制请求不伪装成功 |
| 后端不支持监控 | 显示不支持，隐藏无意义的 CPU/内存图 |
| 无权限 | 说明当前账号不可执行，不无限重试 |
| 远程桌面断开 | 只影响该连接能力，不直接把整个电脑标为离线 |

### 运维操作的作用范围

停止一次 Run、停止 Workspace、断开电脑和撤销凭据是四件不同的事。聊天里的停止只控制当前 run；Workspace 的停止放高级管理，并展示其影响的运行任务。环境级操作最终作用范围和确认信息应由服务端提供。

快照页先展示时间、状态、备注和可恢复范围。恢复前要核对是否覆盖工作文件、是否需要停机、是否影响当前运行；**快照恢复不等于聊天历史回滚**，除非服务端明确如此定义。当前观察到的空快照面板不足以回答这些语义，需 maintainer 确认。

资源限制页按 backend 区分硬限制、软统计或不支持。本次存储字段已经有 VM hard limit / 容器 soft limit 的说明，移动端应保留，而不是只剩一个无解释的 GiB 输入框。

环境级控制放入独立 operation 状态：已提交、处理中、成功/失败/结果未知。手机离线不意味着操作取消；回前台按 operation ID 核对结果，不能重复点击就重新启动一次恢复。

远程 Terminal / Browser / Desktop 后续使用全屏工具页。需要专门设计键盘工具条、视口缩放、触控模式、连接恢复和返回栈；不能把桌面面板缩进 390px 宽度就视为完成。

## Memory：保留独立的内容管理

Memory 是 Bot 的长期记忆内容，当前界面已有搜索、分类、条目和关系图。移动端建议从 Bot 详情进入，默认展示条目列表、分类筛选与搜索，点击查看内容和已有元数据。

关系图作为二级视图：小屏首屏的大图容易占据查找入口，节点标签也容易拥挤。首版可以提供条目的“相关记忆”列表，完整图交互后续加入；关联列表需要服务端相应读能力。

内容修正/删除与索引同步/Compact 分开。前者改变记忆，后者可能触发后端处理；下拉刷新仅更新视图，不自动执行 Manual sync。记忆配置服务的 embedding/backend 选项继续放全局管理，不混入条目编辑器。

当前文档不推断条目中数值的业务含义，也不假设每个记忆已有可跳转的来源 Session；这些需以正式字段为准。

## 管理：按对象分组

建议管理页使用入口列表，而不是一屏展示桌面全部配置表单：

- Bots：打开 Bot 详情；默认行为、访问权限、工具审批策略、能力和高级配置。
- 模型与服务：Providers、Search/Fetch、Voice、Video、Memory backend、Email。
- 能力目录：Supermarket；连接器、MCP、Skills 的可用性与授权由具体 Bot/服务决定。
- 团队：成员、权限、用量、订阅概览。
- 连接与账号：部署、登录、设备会话、退出。
- App：通知、语言、外观、字号、缓存与诊断。

Platforms 是消息进入/离开 Bot 的渠道，Connectors 是 Bot 调用服务能力的连接，MCP 和 Skills 又有各自配置。可在“能力与连接”下分组，但不能隐藏这些差别导致用户把接入聊天平台当成授权 Agent 操作整个外部账号。

跨团队切换时，禁止把旧 Team 的待确认发送、文件上传或环境控制投递到新 Team。用量/订阅先做只读概览，购买和充值在实际发布路线确定后单独设计。

## 范围优先级建议

| 级别 | 内容 | 完成标准 |
| --- | --- | --- |
| 首版核心 | 登录与 scope、Bot/会话、可靠聊天、运行状态、有效的停止与决策、基础文件查看/上传/分享 | 完成断网/进程终止恢复纵切；不重复执行，阅读位置保留 |
| 首版日常体验 | 四区导航、跨 Bot 摘要、执行环境只读详情、模型/位置选择、定时任务基础、记忆列表 | 常用工作能从手机发起、找到结果并理解状态；依赖的聚合协议要落地 |
| 后续增强 | 文件编辑、完整记忆管理、通知、成员管理、更多服务授权、环境级控制 | 有冲突/幂等/权限契约和真机验证；通知优先级可随内测需求提升 |
| 高级后置 | Terminal/Browser/Desktop 深度交互、Hooks 编辑与运行测试、复杂 MCP/Provider 配置、完整快照恢复管理 | 逐个设计移动流程，不追求桌面功能数量对等 |

这是产品范围建议，不是对既有阶段编号重新承诺日期；实施阶段仍遵循 [技术计划](01-product-and-stack.md)。特别是审批/停止如果无法可靠确认，不能为了赶范围用不确定的乐观 UI 代替。

## 需要增加或对齐的协议信息

在已有 [同步草案](03-sync-contract.md) 上，实际界面盘点新增以下重点：

1. Agent、model 和 workspace target 的可用性及设置生效范围；请求绑定不可变执行意图。
2. 文件的 location、path、revision/asset 身份、权限和来源关联；区分工作文件、产物与下载副本。
3. 当前 Team 下按权限过滤的 Bot/Session/运行摘要/定时执行聚合，不默认全局可见。
4. 环境状态的新鲜度与逐项 capabilities：文件、exec、desktop、metrics、limits、snapshot 等。
5. 环境级操作的身份、幂等、结果查询与影响范围，避免用 run abort 协议包揽所有运维。
6. 快照和 Bot 备份分别覆盖哪些数据，以及恢复是否影响会话、决策和正在运行的任务。

这些字段的最终名称和接口与 maintainer 共同确定；本轮只确认产品需要的语义。

## 下一轮最值得验证的交互任务

让用户用线框走四条路径：从首页处理一个等待项；从聊天打开文件再回原位置；确认 Agent 和执行电脑后发送；查看定时任务的上次结果。再比较“资源独立主入口”是否确实降低寻找成本。

四区导航、资源页结构和首版范围均待用户讨论。技术栈、Android 优先、可靠恢复目标、首页兼顾两类工作已确认。
