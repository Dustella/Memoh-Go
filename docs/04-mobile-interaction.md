# 移动端交互草案

更新：2026-09-13（初稿 2026-09-12）。状态：交互讨论稿，无视觉稿或已实现界面。用户已确认首页需要同时兼顾并行任务与深入聊天；以下具体布局仍为建议。

手机首版固定竖屏。横屏和大屏/平板布局后置，后续按独立信息架构与布局任务讨论。

第二轮已按实际 Electron 功能盘点更新顶层入口；资源与执行环境的详细方案见 [功能分区设计](06-mobile-feature-areas.md)。四区布局尚未拍板。

## 产品定位

手机上的重要能力是快速看清进展、处理阻塞事项、继续一个思考过程。多个 Session 的并行性通过可扫描的状态与快速切换呈现；深入一个 Session 时，屏幕主要留给正文与输入。

建议首先保证：从待处理事项进入具体上下文，完成操作后能回到原来的聊天和阅读位置。不能只是把桌面侧栏塞进一个抽屉后就算完成移动设计。

## 顶层导航

建议四个主入口：**首页、会话、资源、管理**。资源提供文件与执行环境的日常入口；待处理仍是首页突出区块与可全屏进入的列表。设置层级使用标准栈导航。

首页和会话的职责不同：首页给全局视野，会话页提供历史、搜索、筛选和固定列表。只有一个 Bot、几个会话时减少分组与空白模块；任务数量增加后再展开筛选。

App 冷启动优先恢复上次有效页面；首次启动或用户主动点首页时进入全局视图。首页有“继续上次会话”入口，不能每次回前台都强行导航到首页。

```text
┌────────────────────────────────┐
│ 我的部署 / 当前团队         ▾  │
│ 首页                    搜索   │
│                                │
│ 继续上次会话                   │
│ API 重构 · 刚才读到第 12 轮  →  │
│                                │
│ 等你处理  2              全部  │
│ 待审批 · 修改配置文件        →  │
│ 待回答 · 选择部署区域        →  │
│                                │
│ 正在运行  4                    │
│ 文档整理     正在检查引用    →  │
│ 测试任务     运行中          →  │
│                                │
│ 最近会话                       │
│ 产品讨论 · 有新结果          →  │
│                                │
│  首页     会话    资源    管理 │
└────────────────────────────────┘
```

这张线框用于讨论信息优先级，未确定颜色、字体、图标或最终卡片形式。Task 列表以简洁行呈现，避免每条都占大卡片；默认只展示少量摘要，更多内容进入专门列表。

## 并行 Sessions 的可见性

一行显示会话标题、Bot、最重要的状态、必要的一句结果摘要。状态区分：运行中、等你处理、完成有新结果、异常、信息过期。未读、未处理、运行中是不同概念，不能共用一个数字气泡。

不要按每个 token 对会话列表实时重排。用户浏览期间保持稳定顺序；在明确活动边界或用户返回列表时更新，必要时显示“有新活动”。待处理高优先级，但不能在用户手指落下前把目标行换掉。

深度聊天页顶部点标题打开最近会话/运行中/待处理切换面板。选择 Session 后关闭面板，独立恢复它的草稿、滚动锚点和附件状态。不是让 20 个完整聊天页面永远驻留；通过本地数据和轻量视图状态实现恢复。

跨 Bot 会话显示来源。跨 Deployment / Team 的总收件箱先后置，首版集中在当前 scope；将来若聚合，每个事项明确归属，点击时安全切换到正确账号与团队。

## 聊天页

```text
┌────────────────────────────────┐
│ ‹  API 重构 ▾            ⋯     │
│ Dev Bot · Linux 开发环境       │
│ 上次同步：运行中 · 正在同步    │
├────────────────────────────────┤
│ 用户输入                       │
│                                │
│ Agent 正文                     │
│ 工具执行摘要            展开   │
│ 产物：设计说明.md           →   │
│                                │
│              ↓ 有新内容        │
├────────────────────────────────┤
│ 输入消息…                  ＋  │
│ 排队发送 ▾               发送  │
└────────────────────────────────┘
```

顶部只保留有助于理解当前任务的 Bot、执行环境和可信状态；CPU、内存、协议版本等进入详情。当前 run 的等待决策用有上下文的卡片呈现，能打开工具参数、文件差异或问题内容，再执行批准/拒绝/回答。

正在运行时，输入框明确显示是“排队发送”还是“立即补充给 Agent”；按 runtime capability 提供 steer。不能把“发送下一条消息”“修改当前任务方向”“停止运行”塞进同一个含糊动作。

原始工具参数、日志、推理内容和子任务过程默认折叠到活动详情，正文保持可读；需要时能展开，且展开状态跨切换恢复。停止请求显示确认中/失败/已停止，并提供明确结果，不能点击后直接移除正在运行的气泡。

## 阅读位置是独立产品状态

建议保存以下逻辑锚点，而不是数组 index 或一个裸 scrollTop：

```text
Scope + session_id
turn_id + block_id + block 内偏移
锚点内容版本 / 必要时字符偏移
相对视口偏移 dp
是否跟随最新内容
展开状态、输入草稿、待发送附件引用
```

block_id 必须稳定或可从规范内容稳定映射；随机重建 AST ID 无法恢复。图片和代码字体加载前预留尺寸；分块渲染既要控制内存，也要保证跨块选择复制。

| 场景 | 建议行为 |
| --- | --- |
| 用户在底部看流式回复 | 保持跟随最新，减少位移动画 |
| 用户向上读历史 | 立即退出跟随模式，新增内容只提示 |
| 用户点“有新内容” | 明确跳到最新，再恢复跟随 |
| 回前台/重连/快照替换 | 保持原语义锚点和视口偏移，不滚到顶部或底部 |
| 加载更旧分页 | 前插内容后抵消高度变化，当前可读行不移动 |
| 图片加载/Markdown 完成校正 | 锚点保持，允许局部布局调整 |
| 锚点所在消息被删或重试替换 | 定位最近仍存在的上下文，轻提示“原内容已更新” |
| 改字号/键盘开合 | 重新测量，用语义锚点恢复，不生搬旧像素值 |

自动跟随和主动发送后的定位规则分别设计。首版建议已在底部时新发送继续跟随；读历史时发送则明确切到新输入位置。不能照搬示例的发送动画而牺牲可预测性。

草稿按 Session 隔离。无网络时可继续写、查看已缓存内容；按发送后显示“等待联网发送”，并可取消尚未提交的本地任务。已经提交但确认未知时不能把本地取消伪装成服务端取消，应显示结果待核对。

## 待处理事项

建议收件箱的首要内容是等待审批、等待回答、执行异常；完成结果可放“新结果”筛选，避免用户把“读过”误当成“处理过”。

每项带具体来源与当前状态。点击进入决策上下文；操作后根据权威响应更新收件箱，再返回此前位置。另一设备已经处理时显示“已在其他设备处理”及最终结果，不继续提交旧问题。

推送点击也走同一路由。如果任务已经完成、被删除或权限撤销，显示正确结果/不可访问原因并给出返回位置；不要新建一个空白 Session 来兜底。

对于多个等待审批事项，首版不做脱离上下文的一键全部批准；可批量标记已读，但已读不能改变服务端决策。

## Artifacts 与工具界面

聊天里显示产物卡片，点击进入全屏阅读器。顶部保留来源 Session 和返回；阅读器自己的滚动位置与聊天位置分别保存。可以从会话标题或菜单打开本会话产物列表，不在窄屏强行常驻左右两栏。

首版建议支持 Markdown/纯文本、代码、图片和文件下载/系统分享；HTML、PDF、交互图表、diff 等按实际需求补充。若使用局部 WebView 展示 HTML 产物，应隔离登录凭据、原生桥与脚本权限；产物中的代码不能直接访问 App 的控制 API。

远程文件浏览、终端、Browser/Display 是 Runtime 的不同能力。先提供产物和基础文件查看，再决定是否做远程终端；保持一屏一事，返回后聊天原地不动。平板/折叠屏后续可以增加双栏，不让手机导航依赖桌面 Dockview。

## 设置与 Runtime 管理

按照作用范围组织设置，避免用户误改全局：

| 范围 | 入口与内容 |
| --- | --- |
| 当前 Session / 下一次执行 | 聊天标题或输入附件区附近：模型、推理强度、运行目标、队列；明确何时生效 |
| Bot | 管理 → Bot：模型默认值、权限、工具、记忆等；首版只做常用项 |
| 执行环境 | 管理 → 执行环境：在线状态、能力、绑定、允许的资源配置 |
| Team / 协作空间 | 顶部 scope 切换与管理入口；按正式 Cloud 契约提供成员/权限等 |
| 连接与账号 | 管理 → 连接：地址、账号、重新登录、切换、删除本地连接 |
| App | 通知、外观、语言、缓存、诊断 |

原生移动端保留一套稳定入口，但资源操作按权限显示。对无权或不支持的功能区分原因；不把服务端管理员的全部设置一次搬上手机。

用户调整模型或运行环境时，界面明确“下一次执行生效”或展示服务端实际语义。删除 Runtime、撤销凭据、变更权限等操作显示作用对象和影响，不能在一个无来源的省略菜单里完成。

## 交互验证任务

用同一组任务比较两个低保真变体：A 为本文的混合首页；B 为会话列表顶部加入待处理条。用户已经确认两者兼顾，尚未指定布局，验证应看实际寻找和返回成本，而不是先投入大规模视觉设计。

1. 十个会话中找到正在等待自己批准的任务，理解影响后拒绝，再回到原本阅读的聊天。
2. 读长回复中部时切后台三分钟，回来能认出原阅读位置，同时得知任务已完成。
3. 给运行中的任务追加下一步，能分清排队与立即介入。
4. 打开产物、分享文件、返回聊天，输入草稿与阅读位置都保留。
5. 切换部署或账号，清楚知道自己正在操作哪台服务、哪个 Team。

基本验收包括中文输入法组合输入、系统返回手势、键盘遮挡、长按选择、字体放大、深色模式、TalkBack 标签与状态播报。流式 token 不应逐个触发屏幕阅读器通知；状态变化使用节制的聚合播报。
