# 产品方向、技术选型与阶段计划

更新：2026-09-13（初稿 2026-09-12）。状态：用户已确认 React Native + Expo；产品细节与阶段预算仍为讨论稿；性能数字是拟议验收预算，不是测试结果。

## 已确认的产品前提

用户希望为 Memoh 做独立移动客户端，至少不做 PWA。Android 优先，同时保留 iOS 的架构与发布路线。用户偏好 Vue，也愿意讨论 React Native；关心流式长文本、多会话和移动系统暂停运行后的体验。

手机首版固定竖屏；横屏和大屏/平板适配后置。当前 iOS 配置不声明 iPad 支持。

用户与 Memoh maintainer 可以直接合作，明确允许客户端与服务端共同增加协议。这是架构前提；本轮范围仍是调查、讨论、写文档，不执行服务端改动。

使用方式同时包含长时间深入一个聊天，以及照看多个并行 Agent。首页需要兼顾两者。未来接入 Team、团队协作空间与云端 Runtime；当前先服务自部署用户。

产品承诺建议写成一句话：**离开时放心，回来时接得上；多个 Agent 在做什么、哪里需要你，都看得清。**

“接得上”包含四种独立结果：内容完整、执行状态正确、操作不会重复、阅读和输入位置保留。只做自动重连不能满足这四项。

## 技术选型决定

**已决定采用 React Native + TypeScript + Expo development build。** 用户在第二轮讨论中明确接受此路线，因 Vue Lynx 仍处于 Pre-Alpha，本项目暂不采用，也不再安排双框架验证。以下比较保留为决策依据，不是待执行的候选清单。

这个建议来自交付风险判断，不是“React 一定比 Vue 快”。用户最在意的问题更多落在同步协议、本地持久化、系统生命周期、键盘与列表锚点上；渲染引擎只负责其中一部分。

### 两个需要更新的认知

React Native 的新架构已经改变了旧 bridge 的通信方式。不能用“每个 token 都要经过旧异步 bridge”的印象评估它；JS 计算、Markdown 解析、布局和过大的组件更新仍然可能造成卡顿。[React Native 新架构说明](https://reactnative.dev/blog/2024/10/23/the-new-architecture-is-here)、[性能说明](https://reactnative.dev/docs/performance)。

Vue Lynx 已有 Vue 3 自定义渲染器、SFC、响应式系统以及 Pinia / Router 示例，AI Chat 示例覆盖流式文本、工具卡片与 Markdown。与此同时，调查时其源仓库 README 仍明确标注 **Pre-Alpha**。这些事实应同时考虑：它已经值得实验，但不能把示例功能齐全当作本项目生产可用的证明。[Vue Lynx 介绍](https://vue.lynxjs.org/guide/introduction)、[AI Chat 示例](https://vue.lynxjs.org/guide/ai-chat)、[源仓库状态](https://github.com/Huxpro/vue-lynx)。

Lynx 也不再只有嵌入现有原生应用这一条路：官方文档列出 Sparkling 作为新建 Android / iOS App 的框架。完整比较对象应是 RN + Expo 与 Vue Lynx + Lynx + Sparkling，而非 RN 与一个裸渲染器。[Lynx 应用框架入口](https://lynxjs.org/guide/start/build-with-app-framework)、[Sparkling](https://tiktok.github.io/sparkling/)。

### 比较范围

| 维度 | RN + Expo development build | Vue Lynx + Lynx + Sparkling |
| --- | --- | --- |
| 用户语言偏好 | 需要接受 React / JSX | 更符合 Vue / SFC 偏好 |
| 原生交付 | 独立原生构建，可接入自定义原生模块 | 有完整应用框架路线，必须验证 Vue 与宿主组合 |
| 系统能力 | Expo 已提供数据库、安全存储、文件和通知等模块 | 逐项核对宿主支持和桥接成本；不能借用 Explorer 内置能力作为交付依据 |
| 流式文本 | 需要控制解析、订阅和列表更新范围 | 双线程有价值，同样需要增量解析、列表测量与锚点策略 |
| Web UI 复用 | DOM 组件需重做；纯 TS 逻辑可提取 | Vue 写法可复用更多，但 DOM、事件、组件库仍需适配 |
| 主要不确定性 | 具体 Markdown、动态高度列表、键盘组合的实机表现 | 除这些问题外，还包括 Pre-Alpha 适配层和宿主模块兼容性 |
| 当前结论 | 已选定；验证本项目的性能与系统集成 | 本轮不采用，不安排验证工作 |

Lynx 使用原生元素，不提供浏览器 `window/document`；现有 Vue Web 组件不能直接当成移动原生组件。Memoh 的 Reka、Dockview、markstream-vue 等应按依赖逐一评估。Vue 的熟悉感是优势，但不等于把整个 `apps/web` 搬过去。[Vue Lynx 平台差异](https://vue.lynxjs.org/guide/introduction)。

Expo development build 是带开发工具的自有原生应用，支持自己的原生依赖；不应把 Expo Go 的限制误认为正式应用的能力上限。[Expo development builds](https://docs.expo.dev/develop/development-builds/introduction/)。

当前选型已经结束。后续性能问题先按解析、状态更新、布局与原生模块等层次定位处理；不能预设任何瓶颈都必然来自业务代码，也不因个别卡顿重新开启框架选型。是否允许复杂产物使用局部 WebView，另作交互决策；核心会话、导航、持久化以原生 App 为目标。

## 推荐的技术边界

| 层 | 建议 | 选择理由 |
| --- | --- | --- |
| 客户端语言 | TypeScript strict | 与现有 SDK 及领域逻辑衔接 |
| 领域核心 | 不依赖 React、Vue、DOM 的 TS 模块 | 协议 reducer、outbox、状态机和身份映射可独立验证 |
| 本地数据 | SQLite；RN 路线首选 expo-sqlite | 用事务保存实体和同步检查点，进程被终止后仍可恢复 |
| 凭据 | 系统安全存储；RN 路线首选 expo-secure-store | 与聊天缓存分离，按部署和账号隔离 |
| 传输 | 沿用 REST + WebSocket，新增能力协商与同步契约 | 复用已有准入、控制与订阅协议 |
| UI 状态 | 路由、展开、选中等短期状态；框架适配层负责订阅 | 聊天不能同时由多个缓存系统分别决定真值 |
| 列表 | 先测平台虚拟列表，再定具体库 | 动态高度、历史插入、长消息跨块选择比单纯行数更关键 |
| Markdown | 公共 AST / 块模型 + 原生渲染适配 | 可增量更新与局部失效，避免绑定 Web DOM |
| 测试 | 领域测试 + Linux 服务端契约测试 + Android 真机验收 | 各层各自证明对应问题 |

Expo 的 SQLite 文档明确支持跨应用重启持久化，SecureStore 提供安全键值存储。当前工程已用 `expo install` 锁定并在 Android 真机验证 `expo-sqlite ~57.0.3` 与 `expo-secure-store ~57.0.4`；数据库迁移方案和列表版本仍在对应纵切/基准中决定。[SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/)、[SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/)。

建议本项目保持独立仓库，通过版本化协议包与 Memoh 协作；不要复制全部后端或引入 Electron 壳。上游 SDK 的 REST 类型可复用或重新生成，WS 协议类型需要单独发布；详见调查文档。

## 性能问题怎样验证

把耗时拆成网络接收、协议归并、数据库批量写入、Markdown 解析、组件更新、文本布局、列表测量和绘制。先定位瓶颈，才决定换库、移到工作线程或补原生模块。

建议的实现原则：

- token 先进入传输缓冲，连续文本合并后以约 30–50ms 的窗口更新可见内容；关键状态与审批单独及时提交。窗口是起点，应按延迟和耗电测量调整。
- 只更新当前变化的内容块；已完成 Markdown 块复用，未闭合代码围栏等保留可变尾部。禁止每个 token 重新解析整段历史。
- Markdown 语法可能让前文重新归类，例如引用定义或未闭合结构。采用有界失效区间，结束时做一次完整校正；不能把所有“旧块”永远冻结。
- 超长单条消息分块虚拟化；不能只虚拟化消息行，却让一个消息节点包含几十万字符。
- 后台会话更新摘要，不持续解析、排版所有会话正文。并行能力应主要消耗服务端资源。
- 存在过载时限制渲染刷新率、延后高亮和图表；协议落地或补快照继续保证正确性。不能静默丢弃无法恢复的业务事件。
- UI 读模型以内存投影加本地持久化为基础，不逐 token 触发整库查询。正文更新可合批，持久 cursor 必须对应同一事务内真正落盘的数据。

### 共用真机基准草案

RN + Expo 使用确定性事件源、固定文本、图片尺寸和故障脚本，在 release 构建上测试。记录设备型号、Android 版本、内存、刷新率、框架与宿主版本，保留 trace。开发模式帧率和宣传 benchmark 不作为结论。

| 场景 | 建议数据与动作 | 验收关注 |
| --- | --- | --- |
| 长历史 | 10,000 条本地消息，分页读取；当前单条 100,000 字符 | 只物化可见窗口，能定位中部锚点 |
| 流式 | 当前会话 100 个小增量/秒，突发 500 个/秒 | 测量合并后延迟、输入响应和内存；这是压力场景，不是假定模型速度 |
| 并行 | 20 个运行会话，其中 1 个正文可见 | 隐藏会话只更新摘要，切换不重建整个应用 |
| 富文本 | 中文/英文/emoji、围栏代码、表格、链接、图片 | 分片 Unicode、未闭合语法、复制选择与高度变化正确 |
| 恢复 | 断网、切后台、进程被终止、服务端重启 | 内容收敛、命令去重、阅读锚点、输入草稿均正确 |

拟议预算：目标 60Hz 中端 Android 上交互期间掉帧比例低于 5%，点击到可见反馈 p95 低于 100ms；暖恢复本地聊天 p95 低于 500ms；在 RTT 150ms、可用带宽 5Mbps、100 条补差且无大附件条件下，权威状态同步 p95 低于 2s。阅读锚点在布局稳定后偏移不超过 8dp；连续 30 分钟压力测试内存进入稳定平台而不持续增长。这些均需先建立可测基线，再讨论是否调整，不能宣称已经达成。

## RN + Expo 的实施验证门槛

选型已确定，验证用于确定组件与实现方案。进入开发阶段后，用以下结果约束第一条纵切，不再安排 Vue Lynx / Sparkling 样例。

1. 自己包名的 Android APK，在 release 模式、断开开发服务器后运行，不能仅用 Expo Go 演示。
2. 导航、系统返回、中文输入法、选择复制、安全区和动态键盘处理正确。
3. SQLite 事务、安全存储、鉴权 WS、生命周期、文件选择和核心恢复场景实际跑通。
4. 以真机基准决定虚拟列表、Markdown 分块与更新策略，保留测试记录。
5. iOS 与上述模块有具体实现路径；在投入完整产品前做最小编译验证。Windows/Linux 开发环境不能代替 macOS/Xcode 的 iOS 验证。
6. 明确需要补充的原生模块和平台差异，不把它们藏在通用 UI 层。

协议核心与压测夹具保持独立，方便验证；不为未来假想的框架迁移提前造通用 UI 框架。

## 交付阶段与退出条件

| 阶段 | 产出 | 退出条件 |
| --- | --- | --- |
| P0：讨论与协议定稿 | 本文档组、上游差距表、交互方向 | 区分已确认约束与建议，明确第一批协议范围 |
| P1：风险验证 | RN + Expo 最小真机样例、测试记录、组件决策 | 键盘、列表、持久化与恢复实现路径明确 |
| P2：可靠聊天纵切 | 连接自部署、登录、会话、发送、流式、SQLite、恢复、停止/决策 | ACK 丢失、App 被终止、离线历史补齐、锚点恢复等关键测试通过 |
| P3：并行任务体验 | 混合首页、跨 Bot 待处理、队列、产物查看、基础 Runtime 信息 | 20 会话场景可定位待处理事项，返回原聊天状态保留 |
| P4：日常使用内测 | 推送、附件、诊断、升级迁移、账号隔离 | 在用户真实自部署与目标 Android 设备上完成故障验收 |
| P5：扩展 | Team 接入适配、更多 Runtime 配置、iOS 发布 | 基于实际 Cloud 契约与权限模型验证，不能只通过 mock |

Team 隔离键、能力协商和 iOS 平台接口从 P1/P2 开始保留；P5 延后的是完整产品功能，不能延后数据边界。复杂远程桌面、完整终端、多文件编辑和全套服务管理建议后置。

第一项真正值得实现的纵切：发送一次任务 → 切后台 → 杀掉 App → 服务端完成任务 → 再次打开 → 仍在原阅读位置，能看到完整结果且任务只执行一次。它比先铺满设置页更能验证这个项目的价值。

## 下一轮需要讨论的内容

- “并行 Sessions”最常见规模、是否跨多个 Bot / 多个部署；目前按 20 个运行会话设计压力场景，不作为用户需求事实。
- 目标 Android 真机及是否有无 GMS 环境；推送方案据此定，不能预设所有设备都可用 FCM。
- 首版产物是否以 Markdown、图片、文件为主，以及是否需要 HTML 预览、远程终端。
- 与 maintainer 对齐 Team / 协作空间的正式名词、Cloud 登录和路由契约、协议维护与兼容周期。

这些问题不妨碍完成本轮规划；进入依赖它们的实施阶段前再定。
