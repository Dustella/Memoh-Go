# 渲染基准与列表/Markdown 决策（P0.4）

更新：2026-09-28。状态：模拟器 release 基线已完成并据此作出**暂定**决策；实体机 2206123SC 复测后定稿。

## 方法

- 构建：release（`EXPO_PUBLIC_BENCH=1`，Hermes，x86_64），不连 Metro。开发构建的数字不可用（同场景 JS 掉帧 50% vs release 16%）。
- 驱动：`node scripts/run-bench.mjs --serial <adb-serial>`，每组合冷启动进程，深链 `memoh://bench?list=…&scenario=…&auto=1` 自动运行；结果写入 `tests/performance/results/`。
- 指标：JS 线程掉帧（rAF 间隔）、UI 线程卡顿帧（`dumpsys gfxinfo`）、可见延迟（入队 → React 提交）、挂载时间、Hermes 堆、前插锚点偏移（`measureInWindow`）。
- 行模型：**一行 = 用户消息或 assistant 的一个 Markdown 块**，超长消息按块虚拟化。流式文本按 33ms 窗口合批，只重扫未闭合尾块（`src/ui/markdown/blocks.ts`，增量 ≡ 全量已测试）。
- 场景：流式 100/s、突发 500/s（各含 200 条历史）、1 万条历史扫动、10 万字单条扫动、1000 条历史中部锚定后前插 5×50 条。

## 结果（Android 15 模拟器，x86_64）

原始数据：`tests/performance/results/android-sdk-built-for-x86-64-android-15-2026-09-28T12-33-37-655Z.md`。

| 场景 | FlatList | FlashList 2 | Legend List 3 |
| --- | --- | --- | --- |
| 流式 100/s：UI 卡顿 / 可见延迟 p95 | 67.8% / 66ms | **33.9%** / 66ms | 67.1% / 65ms |
| 突发 500/s：UI 卡顿 / 可见延迟 p95 | 75.5% / 66ms | 67.2% / 64ms | **49.2%** / 68ms |
| 1 万条历史扫动：UI 卡顿 | 20.3% | 40.8% | **14.5%** |
| 10 万字单条扫动：UI 卡顿 | 24.4% | 34.6% | **14.9%** |
| 前插锚点偏移 | **丢失** | **0px** | 1.1px |
| 挂载 | 52–90ms | 62–137ms | 97–177ms |

JS 线程掉帧三者均在 14–22%，模拟器上 JS 不是区分因素；可见延迟 p95 均约 65ms（33ms 合批窗口 + 一次提交），满足“点击到可见反馈 < 100ms”的预算。

## 结论

1. **FlatList 淘汰**：前插历史时锚点丢失，恰好违反“回来时接得上”的核心要求。
2. **暂定 Legend List 3**：扫动长历史与超长单条的 UI 卡顿最低（约 FlashList 的 1/3），前插锚点稳定（1px），突发流式最好；代价是挂载慢约 50ms，可接受。
3. **FlashList 2 作为备选**：稳态流式 UI 卡顿最低、锚点 0px，但长列表扫动明显更差。若实体机上 Legend 的流式卡顿不改善，再比较两者。
4. **Markdown**：`marked` lexer + 原生 Text 渲染 + 块级缓存保留。可见延迟与 JS 掉帧没有显示解析是瓶颈；不引入 WebView。
5. **合批窗口** 33ms 保留。

以上 UI 卡顿百分比来自模拟器（软件渲染，绝对值偏高）；只用于**相对**比较，不作为性能预算是否达标的结论。
